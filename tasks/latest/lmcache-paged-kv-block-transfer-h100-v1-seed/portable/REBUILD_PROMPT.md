# Rebuild Paged-KV Block Transfer (suite v2) on a qualified whole-GPU host

Use this task bundle to reproduce the Work/Judge images and qualify a new
single-CUDA deployment. You may use Codex, Claude, or another build agent, but
do not let the build agent redesign the benchmark. This file describes how to
build, verify and run the task; the task itself (metric, gates, suites) is
defined by the task JSON, the `portable/*.json` manifests and the Judge.

Preserve these scientific identities byte-for-byte:

- the TaskCore and its resource manifest;
- the seeded kernel_v001, the frozen `transfer_abi.h`, the 25 edge fixtures
  (run by both Work and Judge), the 155-case public table
  (`images/work/benchmark/public_cases.json`) and the 843-case root-only final
  holdout generated by `scripts/generate_final_manifest.py` from the Mooncake
  FAST'25 traces;
- the bit-exact oracle, the same-run bandwidth-envelope protocol, the
  settle/median timing protocol, the payload-bandwidth formula and the
  weighted four-group metric (device, host, trace, overlap) with
  stratified, tier-balanced family scores, the overlap foreground protocol and
  the duplex two-stream protocol;
- the agent-facing optimization contract.

## Evaluation policy

The evaluation policy is `full-final-shared-v3` with selection protocol
`lmcache-shared-final-v3`. Every admitted `auto-*`, `agent-*`, `manual-*` and
`candidate-*` round executes the complete frozen
`lmcache-kv-transfer-final-holdout-v2` suite: 843 scored cases and 25
additional edge gates. Timing, thresholds, aggregation and private input
isolation are identical across these rounds. Interactive rounds keep their
original identities and cannot override `FINAL_VERSION`; host replay keeps its
candidate override. Local public tests inside Work use the disclosed public
suite.

Before formal precheck, the launcher stages the exact run-level
`experiment-manifest.json` bytes at `<task_run_root>/experiment-manifest.json`,
bound to the SHA-256 it recorded when it created the run manifest. Staging
rejects a changed source, symlinks and an existing destination, and creates
the task copy with mode `0600`. The precheck reads this task-local copy and
never falls back to a parent directory.

## 1. Host prerequisites

`docs/HOST_PREREQUISITES.md` lists everything that is not task-specific:
Docker >= 24 with the **NVIDIA runtime as default**, your user in the `docker`
group, `uv` with Python 3.10-3.13, `jq flock rsync patch git sha256sum
nvidia-smi`, CPU `torch` + `numpy` in the repo venv, >= 150 GB free on Docker's
data root, and outbound access to Docker Hub, Hugging Face and GitHub. Check
them first.

Task-specific extras:

| Extra | Why |
| --- | --- |
| **>= 16 GiB of pinnable host memory**, and a `ulimit -l` that allows it | the host and trace arms put chunk objects in mapped pinned host memory; the profile features say `pinned-host-memory` / `pcie-host-transfer` |
| the GPU **directly attached**, with its PCIe generation and width recorded | 45 % of the score weight measures the host platform, not the GPU (section 9) |
| 48 GiB of host RAM for the Work container, 64 GiB for the Judge | task JSON `work` / `judge` `cpu_limit` and `mem_limit`; the container CPU quota measurably affects timing |
| `ss` (iproute2) | the launcher refuses to start when the coordinator port is already listening |

No model, tokenizer, dataset or private corpus is needed: payloads are seeded
random bit patterns. `scripts/build_images.sh` has no mandatory task-specific
environment variable.

**Network.** Work never has direct egress. The launcher runs Work on a per-run
`--internal` Docker network whose only peer is a task-owned CONNECT sidecar
(`scripts/restricted_proxy.py`, run from the Work image) that relays the Judge
port and allows TLS tunnels to the model-authentication hosts
(`api.openai.com`, `auth.openai.com`, `chatgpt.com`).
`scripts/run_fixed_budget.sh` reads the task JSON's `internet` flag: the task
JSON sets `internet: true`, so the sidecar also runs with
`--allow-public-egress` (CONNECT to any globally routable host on ports 80/443;
loopback, private, link-local, CGNAT, multicast and reserved addresses are
refused) and Codex runs with live web search. With `internet: false` the
sidecar keeps the allowlist only and Codex keeps its offline flags and prompt.
`scripts/sforge_isolated_entry.py` places Work on that network and applies the
flag. No host iptables and no host proxy are needed; a preflight from inside
the network proves that direct egress fails and that the sidecar answers as
configured before the agent budget starts. The agent-facing instruction that
forbids copying external implementations is backed by the optional LLM
integrity review.

## 2. GPU envelope

The task JSON's `portable.execution_profiles` carries exactly one profile,
`single-cuda-sm80-64g`: `count = 1`, `min_compute_capability = "8.0"`,
`min_memory_bytes = 68719476736` (64 GiB), features `cuda / nvcc /
pinned-host-memory / pcie-host-transfer / bf16-storage`. MIG is not qualified.

Who enforces it:

- `runtime/kv_transfer_runtime.py` carries `MIN_COMPUTE_CAPABILITY` and
  `MIN_DEVICE_MEMORY_BYTES` and asserts them in `hardware_inventory()`, which
  also refuses anything but **exactly one visible CUDA device** ("exactly one
  CUDA device must be visible");
- `images/judge/verify_kv_transfer.py` carries the same pair of constants —
  the tests assert the two copies are equal — and reports them as the scored
  `hardware_ok` gate;
- the launcher preflight in `scripts/lib.sh` requires `GPU_MIN_FREE_MIB` free
  (default 65536) before it touches Docker, and
  `scripts/single_gpu_runtime_preflight.py` checks the harness contract and the
  nine portable digests first.

The 64 GiB floor covers the largest Judge case: a 40 GB engine pool, one
regenerated pool layer for verification, up to 2.5 GiB of chunk payload on the
device, the 256 MiB scratch and the overlap foreground (about 2.4 GB). Every
qualified card (H100 SXM 80 GB, H100 NVL 94 GB) clears it. The runtime also
allocates one 4 GiB pinned host arena before the candidate loads; that is
separate from the device floor.

The GPU model and UUID are provenance only, and so are the PCIe generation and
lane count — none of them is a gate. The compile target is **not** a fixed
architecture: `native_arch()` reads the allocated GPU's native `sm_XY`, adding
the `a` suffix on Hopper and newer, and the frozen nvcc command uses that.
Nothing needs changing to move to another architecture.

### The holdout instance is frozen, not drawn per build

The final holdout instance is **frozen, not drawn per build**. The
qualification draw is committed inside the task at
`judge/private/final_cases.json` and is what `build_images.sh` reads by
default; `final-suite-manifest.json` records its SHA-256 under
`frozen_instance`. It is Judge-only: it is staged mode 0600 into a root-only
Judge build context and must never be copied, mounted or described inside the
Work image (`scripts/validate_layout.py` proves no Work build context admits
it, by path and by SHA sweep). `build_images.sh` does not draw anything: it
enforces that the source is a regular non-symlink file with
`suite_id == lmcache-kv-transfer-final-holdout-v2` and exactly **843** scored
cases, and that the staged build-context copy is mode 0600, owned by the
building user and byte-identical.

**Expected digest:** `final_cases.sha256` in the build manifest must equal
`434cab78100ff814a75bde423945deb595384a17b5191b47dccce757db756145`.

The portable manifests freeze both the *rule* and the drawn instance: three
layers whose case identities are mutually exclusive but drawn from one
distribution, each covering both layouts, both arms, both directions and all
three chunk scales, with case ids unique and every score group covered.
`scripts/generate_final_manifest.py --redraw --seed <int>` draws a
reproducible *new* instance from a seeded `random.Random`; that is a **new
suite identity** whose `frozen_instance` record must be updated, and no
earlier score is comparable to it. `FINAL_CASES_PATH` overrides the default
when you deliberately want to build against another instance.

There is **no per-deployment capture** in this task: payloads are seeded
random bit patterns generated inside the runtime.

The Work image starts from only `images/work` plus the pinned `runtime/` build
context (`task_runtime=runtime/`); the Judge image is built independently from
`images/judge`, the same runtime context and the private `final_cases` context.

## 4. CPU checks before any image or GPU operation

From the task root:

```bash
python3 -B -m pytest -p no:cacheprovider tests -q
python3 -B scripts/validate_layout.py .
find scripts -maxdepth 1 -name '*.sh' -print0 | xargs -0 -n1 bash -n
```

Those tests recompute the scientific resource digest, delivery/build-resource
digest, manifest byte digests and real suite case counts. Treat any mismatch
as a hard stop. The task JSON intentionally is not a member of either resource
manifest because it is the root document that binds their digests; each
resource manifest also excludes itself to avoid a recursive hash. After a
legitimate edit to a hashed file, `scripts/refresh_portable_manifests.py`
recomputes the digests (`--check` reports drift without writing).

Run the suite in an interpreter that has Torch and the SForge orchestration
dependencies (the repository venv). On an interpreter that lacks the `docker`
module, the tests in `tests/test_single_gpu_migration.py` that fork
`scripts/single_gpu_runtime_preflight.py` fail with a different error string;
the preflight's fail-closed behaviour is still correct.
`scripts/validate_layout.py` passes on a clean checkout.

`tests/test_scoring.py` asserts that `native_arch` maps cc 9.0 to `sm_90a` and
cc 8.6 to `-arch=sm_86` with no `sm_90a` anywhere, and covers the envelope
protocol constants; `tests/test_portable_contract.py` recomputes the nine
`portable/*.json` digests and case counts from the runtime, the Judge adapter
and the generator.

## 5. Build

```bash
bash scripts/build_images.sh
jq -e '.source_digest and .work.id and .judge.id and .final_cases.sha256' \
  ../../../outputs/lmcache-paged-kv-block-transfer-h100-v1-seed/build/image-manifest.json
```

`build_images.sh` needs `docker` (or docker-group membership), `jq` and
`sha256sum`, plus a working `sforge` and `python` from the repository venv. It
runs `validate_layout.py`, validates the holdout as described above, builds
the Work and Judge images, and computes the image source digest **before and
after** the build, failing with "image-driving source changed during build" if
it moved; the manifest hashes are re-checked too. It writes
`build/image-manifest.json` (schema 2) with both image IDs and
`final_cases{sha256, suite_id, case_count}`.

Both `scripts/` and `tasks/` are inside the image source digest: **after
editing any script you must rebuild**, or the runner's image-freshness check
refuses to start.

Keep the source digest, the exact Work/Judge image IDs and the final holdout
digest with the run. Do not substitute a pre-existing tag without verifying its
recorded image ID.

## 6. Post-build verification

```bash
PHYSICAL_GPU=<index> bash scripts/smoke_test.sh --oracle
```

This runs the full lifecycle on the target card. Expected values:

- all 25 edge cases and all 155 public cases bit-exact, **all 8 gates 1.0**;
- the seed on the 20-case frozen holdout `fbdab65a…` reads about
  **241–245 GB/s** on an H100 NVL under envelope protocol v2. Expect about 2 %
  run-to-run noise from one Judge process to the next on the same card, and
  about 1.7 % between cards of the same model. Since the holdout instance is
  frozen (section 3), that spread is measurement noise on one suite, not two
  suites.

**Read the envelope probe record before trusting the host arm.** The result
carries `device_gbps`, `h2d_gbps`, `d2h_gbps`, `zerocopy_h2d_gbps`,
`zerocopy_d2h_gbps` and the `host_gbps` that is the best of the four host
probes. Two checks:

1. The best host probe should be close to the slot's nominal PCIe rate —
   Gen3 x16 about 15.8, Gen4 about 31.5, Gen5 about 63 GB/s. A probe far below
   that means the card sits behind a switch or on a slow NUMA path, and the
   host arm is scoring the platform rather than the candidate. On an H100 NVL
   reference host `host_gbps` is about 57.5 GB/s, 91 % of the Gen5 x16
   nominal.
2. Compare `h2d/d2h_gbps` against `zerocopy_h2d/d2h_gbps`. If they differ by
   more than the 1.10 margin, a copy-engine-only ceiling would be the wrong
   model on this host; protocol v2 probes both paths so that the envelope
   covers whichever is faster.

**On a new card the oracle must pass every gate before an agent touches it.**

## 7. Formal run

```bash
launch/lmcache-kv-transfer/run.sh \
  --device-uuid GPU-00000000-0000-0000-0000-000000000000 \
  --calibration-epoch campaign-qualified-clock-policy-v1 \
  --judge-port 18496 \
  --model <model> --effort <level> --hours 2 \
  [--allocation-key allocation-sha256:<64hex>] [--lease-id ID] \
  [--run-id ID] [--auth /path/to/auth.json] [--tmux]
```

Qualify one scheduler-allocated whole NVIDIA GPU against the profile above
before this. Record the stable measurement profile (model, compute capability,
memory, driver, image IDs, software ABI, calibration protocol, and a
scheduler-issued calibration epoch tied to a documented clock/power policy).
Record UUID and observed current clocks only in deployment attestation, and
record the PCIe generation and width with the run. Without a calibration epoch,
the run is unqualified for a cross-run leaderboard.

`--device-uuid` must be a scheduler-issued canonical whole-GPU UUID. Single
mode **rejects** `WORK_GPU` / `JUDGE_GPU` and never falls back to the
dual-GPU path, which is reachable only through `--legacy-dual-gpu`.
`--allocation-key` is recomputed by `canonical_allocation_key()` when omitted
and must match when supplied; `--lease-id` is generated once, never reused,
when omitted.

**Budget / interval / cooldown contract.**

| Quantity | Default | Constraint |
| --- | --- | --- |
| `TASK_TIMEOUT` (agent budget) | 7200 s | must be > `EVAL_INTERVAL` and a multiple of 60 |
| `EVAL_INTERVAL` | 300 s | a multiple of 60; the same value is passed as `--submission-cooldown`, so the two are always equal |
| auto evaluation | off | the runner always passes `--disable-auto-eval`; only a manual `sforge-submit` triggers the interactive Judge |
| `FINAL_EVAL_TIMEOUT` | **4800 s** | must match the task JSON's `judge.eval_timeout`. **Do not lower it**: the Judge's own adapter timeout is 4500 s, and a shorter outer timeout cuts the Judge off before it can finish |

The internal ladder is candidate stage 3600 s -> verifier total 4200 s -> Judge
adapter 4500 s (the Judge image's `LMCACHE_KV_*_TIMEOUT` variables), under the
task JSON's 4800 s.

**Ports.** `--judge-port` defaults to **18496** and must be 1024-65535 and not
3128 or 3131 (sidecar ports); the scheduler must allocate a different free one
for every concurrent run on the same host.

**Version store.** `SFORGE_VERSION_STORE_ROOT` must explicitly point at a store
carrying a `.sforge-version-store.json` marker that registers this task id;
`SFORGE_AGENT_RUNTIME_DIR` at an agent runtime built by
`launch/build-agent-runtime.sh`; `CODEX_AUTH_JSON_PATH` at a regular
non-symlink file, mode 0600, owned by the launching user. `RUN_ID` must be
globally unique inside one store — reusing one fails only after the deadline,
with `VersionStoreCollision`, and wastes the whole agent budget.

**Proxy.** The run needs no host proxy: `run_fixed_budget.sh` overrides
`SFORGE_HTTP_PROXY` / `SFORGE_HTTPS_PROXY` / `SFORGE_NO_PROXY` with its own
sidecar's address before Work starts (the experiment manifest records
`network.mode: docker_internal_restricted_connect_proxy`,
`direct_public_egress: false` and the sidecar's `restricted_proxy_sha256`).
The loopback guard in `launch/common.sh` reads the single-GPU wrapper and
refuses a host-loopback ambient proxy, so unset `http_proxy` / `HTTP_PROXY`
(or export a Docker-bridge address) before launching. The build separately
accepts `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` (and lowercase) as
build-args.

## 8. Run artifacts and success criteria

```text
outputs/lmcache-paged-kv-block-transfer-h100-v1-seed/
├── build/image-manifest.json
└── runs/<RUN_ID>/
    ├── resource_lease.json
    ├── completion.json
    └── <task_id>/
        ├── submissions/agent-N/submission.tar.gz   # every accepted manual submission, byte-for-byte
        ├── final_archive.tar.gz                     # the immutable deadline archive
        ├── final_result.json  final_snapshot.json  run_history.json
        └── ...
```

Success means all of: `resource_lease.json` in state **CLOSED**; the launcher
exiting 0; `completion.json` written; and the standalone final reporting
`valid = true` with a positive score.

When the candidate is invalid on the hidden final, the lease still closes
normally but the postcheck reports "independent Judge did not accept the frozen
submission" **by design** and `completion.json` is not written. That is a
candidate-level result, not a protocol failure.

**On failure, look at these first**, in order: `<run>/logs/sforge-run.log` ->
`logs/build/{work,judge}-image.log` (image freshness) -> the preflight output
(UUID flock, NVML attestation, port occupancy) -> the Judge's own record. When
a gate fails, the Judge deliberately hides which one from the candidate: a
zero gate with zero reward/score/groups reports `trusted_gate_failure` (status
FAILED), and anything else reports ERROR with the gate values withheld. The
exact per-case reason lives only in the root-owned, mode-0600 private
artifact.

Two operational rules: serialising runs on one card requires waiting for the
previous run's containers to actually exit, and a duplicate `RUN_ID` fails
only at the very end.

## 9. What to re-measure on another GPU — or another host

There are two independent axes here, unlike the other single-GPU tasks.

**Another card, same host.** Nothing needs re-measuring: the compile target
follows `native_arch()` automatically and the bandwidth envelope is probed in
the same run on the same device. Just change the device UUID. Candidate-to-
candidate comparisons must still be pinned to one card (the scripts enforce
a per-GPU lock); across cards of the same model expect about 1.7 % spread.

**Another host.** This is a **new measurement profile even with the same GPU
model**, because 45 % of the score weight (the host and trace arms) measures
the platform: chunk objects live in mapped pinned host memory and the kernel
dereferences them across PCIe through UVA. Re-measure and re-record: the raw
GB/s under the new comparability key; the PCIe generation and lane count; the
NUMA / root-complex placement, IOMMU state and container CPU quota; the NVML
device-memory peaks of Work and Judge; and the envelope probe record
(section 6). Confirm by hand that the `SETTLE_SECONDS = 0.10` busy-wait barrier
still drains the harness's preparation residue under this host's container CPU
quota — it was calibrated against one quota and one boost policy, and if it is
too short the timing window is contaminated.

Do **not** re-calibrate: the ABI, the two layout families, the 25 edge
fixtures, the holdout's generation rule, the bit-exact correctness contract, the
`device^0.35 x host^0.25 x trace^0.10 x overlap^0.30` weights and the stratified
family aggregation, the overlap
foreground protocol (`OVERLAP_COVER = 3.0`, `MAX_OVERLAP_LOSS = 0.95`), `ENVELOPE_MARGIN = 1.10`,
`SETTLE_SECONDS = 0.10`, the compile flag set, or the suite `manifest_sha256`
values.

**The envelope protocol is part of the calibration-protocol identity.** Results
measured under `same-run-cudamemcpy-probe-v1` and under
`same-run-cudamemcpy-zerocopy-probe-v2` are different measurement profiles even
on the same card, and must never be put in the same table.

Raw scores may be compared only when both runs are qualified and their
recorded comparison identity is identical. That identity is the ordered pair of
the evaluation-contract SHA-256 and the measurement-profile comparability key;
the contract digest is deliberately not folded into the pure machine profile
hash. Merely satisfying the broad `single-cuda-sm80-64g` capability envelope
does not make two runs comparable.
